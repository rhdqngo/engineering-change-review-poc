# Stack Selection

Choose a stack based on target platform, team constraints, validation paths, and the product's core task—not popularity rankings.

## Selection order

1. Respect technology explicitly requested by the user.
2. Confirm already selected deployment, engine, and platform constraints.
3. Confirm an official scaffold and maintainable long-term path exist.
4. Evaluate tests, type/static analysis, UI preview, and capture support.
5. Avoid multiple frameworks that do not serve a real product requirement.

## Common decision dimensions

| Dimension | Question |
| --- | --- |
| Platform | Browser, desktop, mobile, console, or engine? |
| Input | Touch, keyboard and mouse, gamepad, or mixed? |
| Rendering | Documents/forms, dense data, canvas, 2D/3D, or real time? |
| Server | Static, API, real time, or offline synchronization? |
| Team | Existing language, deployment, and operations experience? |
| Validation | Can real UI, input, and state be validated repeatedly or automatically? |
| Lifetime | Short experiment or long-lived product? |

## Selection record

Record in one concise section:

- selected stack
- rationale
- deliberately rejected alternatives
- accepted constraints
- revisit conditions

“Modern,” “fast,” and “popular” are not sufficient reasons by themselves.
