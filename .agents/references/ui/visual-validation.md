# Visual Validation

## Evidence strength

1. Directly run the flow and input in an actual browser, device, or game engine.
2. Use automated browser or simulator interaction with capture.
3. Render the actual component in Storybook or another isolated environment.
4. Use current screenshots or video generated by the project.
5. Review source code and static markup.

Do not claim a higher level of validation when only weaker evidence exists.

## Required observations when applicable

- normal state
- initial loading and background refresh
- empty state, partial results, errors, and recovery
- success, completion, and confirmation feedback
- disabled, unavailable, locked, and permission-denied states
- narrow, medium, and wide supported viewports
- production font, fallback font, and normal viewing scale
- short, typical, long, and localized text; large values; missing images; many items
- unexpected control wrapping, text clipping, and icon-label alignment
- comparison with another screen or precedent using the same semantic role
- the complete set of persistent copy and the explanation-deletion test
- keyboard focus and restoration
- touch targets and scrolling
- gamepad navigation, wrap behavior, and back/cancel
- normal, critical, and notification-overload HUD conditions

## What screenshots alone cannot prove

- focus order
- hover, focus, pressed, and selected transitions
- keyboard or gamepad navigation
- error recovery and input preservation
- layout stability during asynchronous loading
- production/fallback-font transition and real text fit
- whether the task remains understandable after explanatory copy is removed
- animation speed and motion-sickness risk
- time to action in a real-time HUD
- real touch-target conflicts

## Reporting states

- `verified`: conditions and tools were directly checked
- `failed`: a failure and its conditions were reproduced
- `unverified`: tools, data, or platform were insufficient
- `not-applicable`: outside the scope, with a recorded reason

A successful build or type check is not visual evidence. Code, tokens, and component reuse alone cannot pass perceptual comfort or narrative restraint.
